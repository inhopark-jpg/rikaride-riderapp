# Design-to-Dev 변환 규칙

> **다루는 것** — Figma 디자인을 코드로 작성하거나(Figma→코드), 코드를 Figma 컴포넌트로 만들 때(코드→Figma) Claude가 따르는 변환 규칙. 이름 변환(§1~4)과 속성 재선언 처리(§5)를 다룬다.
> **관련 룰북** — `component-structure-rule.md` (레이어 판별 — 이 문서가 전제하는 스켈레톤/템플릿/패턴 구분, 그리고 "패밀리 ≠ 공유 스켈레톤" 원칙은 거기서 가져온다)
> **소비 제약** — 없음.

> 이 문서는 Claude가 Figma와 코드 사이를 오갈 때 "어떻게 쓸 것인가"를 다룬다. 컴포넌트가 스켈레톤/템플릿/패턴 중 무엇인지 판별하는 방법이나 Figma 페이지 배치 규칙 같은 "이 디자인을 어떻게 이해할 것인가"는 `component-structure-rule.md`를 참고하세요. 이 문서는 그 판별이 끝난 뒤의 산출물 — 이름(§1~4), 그리고 레이어 간 속성이 겹칠 때의 코드/Figma 표현(§5) — 을 다룹니다.

---

## 1. 원칙

**Figma 이름이 정본(source of truth)이고, 개발 이름은 그로부터 기계적으로 파생됩니다.** 둘을 따로 정하지 않습니다 — 아래 변환 알고리즘을 그대로 적용하면 항상 같은 결과가 나와야 하고, 예외가 필요하다고 느껴지면 알고리즘이 아니라 Figma 쪽 원래 이름이 잘못된 것인지 먼저 의심합니다.

---

## 2. 변환 표

| 요소 | Figma | Dev (컴포넌트명, PascalCase) |
|---|---|---|
| 스켈레톤 | `.skeleton/btn-ghost` | `_SkeletonBtnGhost` |
| 템플릿 | `btn-ghost` | `BtnGhost` |
| 패턴 | `btn-ghost/pattern-go-back` | `PatternBtnGhostGoBack` |
| 빌딩블록 + 패턴 | `.btn-ghost/pattern-save-item` | `_PatternBtnGhostSaveItem` |
| 패밀리 없는 패턴 | `pattern-loading-overlay` | `PatternLoadingOverlay` |
| 패밀리 없는 빌딩블록 | `.pattern-scrim` | `_PatternScrim` |

---

## 3. 변환 알고리즘 (기계적, 판단 불필요)

1. `.` 접두사가 있으면 → `_`로 대체.
2. `pattern-` 마커가 있으면 → 문자열 맨 앞으로 옮기고 `Pattern`으로 표기.
3. 남은 `family-subgroup` 및 `pattern-name` 세그먼트를 하이픈 기준으로 쪼갠 뒤, 각 단어의 첫 글자를 대문자로 바꿔 공백 없이 이어붙임.
4. 슬래시(`/`)는 최종 결과에 남지 않음 — 슬래시가 구분하던 두 세그먼트(family와 pattern-name)는 이어붙는 순서로만 표현됨.

Figma 쪽에서 이미 확정된 규칙이 그대로 보존되는 지점:

- **템플릿은 접두사 없음** → 개발 쪽에서도 `Pattern`이나 `_`가 없는 이름은 곧 템플릿.
- **패턴은 항상 `Pattern`으로 시작** → 열려 있는 템플릿이 실제로 있는지 여부와 무관하게 동일 적용.
- **스켈레톤은 절대 `Pattern`을 붙이지 않음** → `_Skeleton...`으로만 표기, `_Pattern...`과 혼동되지 않음.
- 스코프(전역/전용)는 Figma에서도 이름에 넣지 않으므로, 개발 쪽 이름에도 영향 없음.

---

## 4. 파일명

컴포넌트명은 PascalCase로 변환하되, 파일명은 프로젝트의 기존 컨벤션을 따릅니다(예: `btn-ghost/pattern-go-back.tsx`처럼 Figma 원본 이름을 kebab-case 그대로 파일 경로에 써도 되고, `PatternBtnGhostGoBack.tsx`처럼 컴포넌트명과 맞춰도 됩니다). 이 문서는 이 선택을 강제하지 않습니다 — 프로젝트마다 다를 수 있는 영역이라 결정론적 규칙으로 못 박지 않습니다.

---

## 5. 속성 재선언 처리 (스켈레톤 ↔ 템플릿)

스켈레톤이 소유한 속성(예: `size`, `loading`)을 템플릿이 그대로 쓰거나 일부만 다르게 써야 하는 경우가 있다. Figma 쪽에는 두 가지 구현 방식이 있다:

1. **중첩 인스턴스 속성 노출(expose)** — 템플릿이 스켈레톤 인스턴스의 속성을 그대로 밖으로 뚫어서 보여준다. 스켈레톤에 값이 추가되면 템플릿도 자동으로 따라간다. 유지보수 비용 없음.
2. **템플릿 자체 속성으로 재선언** — 템플릿이 자기만의 독립된 속성을 새로 만든다. 특정 값에서 색상·동작이 갈라지는 경우 필요하다. 스켈레톤이 커지면 이 속성은 수동으로 갱신해야 한다.

### 5.1 언제 재선언하는가

**기본값은 1번(노출)이다.** 특정 값에서 색상·동작이 실제로 갈라지는 게 확인됐을 때만 2번(재선언)으로 전환한다 (`component-structure-rule.md` §5 "2회 규칙"과 같은 철학 — 불확실한 예외를 미리 방어하지 않고, 실제로 필요해졌을 때만 승격한다).

**판단은 prop 단위다, 템플릿 단위가 아니다.** 한 템플릿 안에서 어떤 prop은 1번(노출), 다른 prop은 2번(재선언)일 수 있다 (예: `btn-primary`는 `size`는 노출, `loading`은 재선언). "이미 다른 prop을 재선언했으니 통일한다"는 이유로 필요 없는 prop까지 재선언하지 않는다 — 그러면 스켈레톤이 커질 때마다 불필요한 prop까지 전부 손대야 한다.

**값의 부분집합만 필요한 경우(예: 어떤 템플릿은 `size-xs`를 지원하지 않음)는 재선언이 아니라 스켈레톤을 분리한다.** `component-structure-rule.md` §3의 "패밀리 = 공유된 정체성이지 공유된 스켈레톤이 아니다"를 그대로 적용한 것 — 겉보기에 같아 보여도 실제 지원 범위가 다르면 같은 스켈레톤이 아니다. 예: `badge-pill`과 `badge-ghost`가 처음엔 `.skeleton/badge`를 공유했지만 `badge-ghost`가 `size-xs`를 지원하지 않는다면, `.skeleton-badge-pill` / `.skeleton-badge-ghost`로 나눈다. 나눈 뒤에는 각 템플릿이 자기 스켈레톤의 값을 그대로 노출(1번)하면 되므로 재선언 자체가 필요 없어진다.

**값의 범위 차이를 "의도적 설계"로 확정하기 전에 근거를 확인한다.** Figma 컴포넌트의 usage description에 명시돼 있거나 사용자가 명시적으로 확인해준 경우만 의도적 제약으로 인정한다. 근거 없이 "이 템플릿엔 해당 프레임이 안 보이니 의도적으로 뺀 거겠지"라고 추측하지 않는다 — 근거를 못 찾으면 멈추고 보고한다 (근사값을 지어내지 않는다는 토큰 규칙과 동일한 원칙).

### 5.2 재선언된 속성을 다룰 때 (사람 · Claude 공통)

재선언된 prop은 기존 스켈레톤의 같은 이름 속성과 나란히(위: 템플릿 자체, 아래: 중첩된 스켈레톤 인스턴스) 노출될 수 있다. 이 둘은 서로 바인딩되어 있지 않다 — 값이 어긋날 수 있다는 뜻이다. **항상 템플릿 자체(위)의 속성만 설정한다. 중첩된 스켈레톤 그룹(아래)의 속성은 직접 건드리지 않는다.** 이 규칙 하나로 어떤 prop이 노출(1번)인지 재선언(2번)인지 사람이 구분할 필요가 없어진다 — 항상 최상단만 보면 되기 때문이다.

### 5.3 코드를 작성할 때

재선언된(또는 분리된 스켈레톤의) prop 타입은 해당 스켈레톤 쪽 타입을 손으로 다시 타이핑하지 않고 참조로 파생시킨다:

```ts
// 전체집합을 그대로 쓰는 템플릿
type BtnPrimaryProps = {
  size: SkeletonBtnProps["size"];
};

// 스켈레톤을 분리한 케이스 — 분리된 스켈레톤 자체가 이미 좁은 범위이므로 그대로 참조
type BadgeGhostProps = {
  size: SkeletonBadgeGhostProps["size"];
};
```

Figma 쪽이 1번(노출)이든 2번(재선언)이든, 코드에서는 항상 이 파생 방식을 쓴다 — Figma 내부 구현 방식이 바뀌어도 코드의 공개 API(prop 타입)는 그대로 유지된다.
