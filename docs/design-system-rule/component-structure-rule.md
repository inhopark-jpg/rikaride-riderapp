# 컴포넌트 구조 규칙

> **다루는 것** — 컴포넌트를 스켈레톤 / 템플릿 / 패턴 3계층으로 판별하는 2단계 테스트, 네이밍 스키마, 페이지 배치 규칙, 라이프사이클.
> **관련 룰북** — `design-to-dev-rule.md` (이름 변환 + 속성 재선언 시 코드/Figma 처리), `color-token-rule.md` (템플릿의 색상 소유), `shape-token-rule.md` (스켈레톤의 dimension 소유)
> **소비 제약** — 스켈레톤은 색상을 갖지 않음 (예외 없음).

> 이 문서는 Figma MCP로 연결된 파일의 컴포넌트를 해석하거나, 새 컴포넌트의 이름/구조를 제안할 때 참고하는 규칙 문서입니다. 사람이 읽는 온보딩 문서가 아니라, 판단 기준을 정확히 적용하기 위한 참조용입니다.
>
> **중요 — 이 문서가 담고 있는 것은 설계 방식이지, 특정 프로젝트의 컴포넌트 목록이 아닙니다.** 여기 나오는 `btn`, `btn-ghost`, `top-bar`, `scrim` 같은 이름은 전부 하나의 예시 프로젝트에서 가져온 것일 뿐이며, 그 이름 자체가 규칙은 아닙니다. 실제로 연결된 Figma 파일에는 이런 패밀리가 아예 없을 수도 있고, 완전히 다른 이름의 컴포넌트들로 구성되어 있을 수도 있습니다. 적용해야 할 것은 각 섹션의 **판별 기준(테스트, 스키마 형태, 배치 순서, 트리거 조건)**이며, 예시에 나온 구체적인 이름을 그 프로젝트에 그대로 기대하거나 강제해서는 안 됩니다. 실제 파일을 읽을 때는 그 파일에 존재하는 실제 family 이름에 이 로직을 대입해서 판단하세요.

## 1. 레이어 (3종류)

모든 컴포넌트는 다음 세 레이어 중 하나입니다.

| 레이어 | 정의하는 것 | 콘텐츠 |
|---|---|---|
| 스켈레톤 (skeleton) | 형태 — radius, height, padding, gap, icon size 등 | 없음 |
| 템플릿 (template) | 스킨 — 색상, 상태(state), 엘리베이션 | 여전히 수정 가능 |
| 패턴 (pattern) | 스킨 + 고정된 의미 | 완전히 고정됨 |

- 스켈레톤은 색상을 가질 수 없음 (예외 없음).
- 템플릿은 콘텐츠(텍스트/아이콘)가 플레이스홀더 상태로 수정 가능.
- 패턴은 텍스트/아이콘 선택/인스턴스 교체 등 콘텐츠 관련 속성이 전부 고정됨. 단, 데이터 값(예: `{item_name}`처럼 데이터로 채워지는 슬롯)은 예외 — 고정된 문구 안의 데이터 삽입은 "수정 가능한 콘텐츠"로 치지 않음.
- "복합 템플릿(composite template)"은 별도 레이어가 아니라 템플릿의 하위 설명일 뿐. 다른 템플릿/패턴을 조합해서 만들어졌지만 콘텐츠가 여전히 열려 있으면 템플릿.

### 레이어 판별 — 2단계 테스트 (순서대로)

**1단계: 이 컴포넌트가 색상/상태/엘리베이션을 소유하는가?**
- 아니오 → **스켈레톤**. (수정 가능한 속성이 0개여도 스켈레톤. "고정 vs 수정 가능" 질문 자체가 이 레이어엔 적용되지 않음.)
- 예 → 2단계로.

**2단계: 텍스트, 아이콘, 중첩된 인스턴스 중 여전히 수정 가능한 것이 있는가?**
- 예 → **템플릿**
- 아니오 → **패턴**

이 두 질문 외에 다른 기준(예: "형제 인스턴스가 다르게 설정할 것인가" 같은 추정 기반 테스트)은 사용하지 않음 — 판단이 관찰자에 따라 달라지는 문제가 있어 폐기됨.

### 중첩 규칙

```
스켈레톤  → 스켈레톤만 중첩 가능
템플릿    → 스켈레톤, 템플릿, 패턴 모두 중첩 가능
패턴      → 스켈레톤, 템플릿, 패턴 모두 중첩 가능
```

- 어떤 레이어든 자기 자신과 같거나 아래 레이어만 중첩 가능. 위 레이어는 중첩 불가 (스켈레톤이 템플릿/패턴을 중첩하면 색상 규칙 위반).
- 패턴이 템플릿 안에 "고정된 기본값"으로 중첩되는 것은 정상.
- 패턴에서 다른 패턴을 직접 파생시키지 않음 — 새 패턴이 필요하면 열려 있는 템플릿으로 돌아가 다른 조합을 고정.

## 2. 플래그 (레이어와 별개, 모든 레이어에 적용 가능)

### 빌딩블록 (building-block)
- 정의: 인스턴스가 화면에 직접 배치되지 않는 컴포넌트.
- 스켈레톤은 항상 빌딩블록.
- 템플릿/패턴도 부모 없이는 의미가 없으면 빌딩블록이 될 수 있음.
- 표기: 이름 앞에 `.` 접두사. Figma에서 퍼블리시되지 않음(같은 파일 내에서는 접근 가능).
- 빌딩블록 여부는 레이어 판별과 무관한 별도 질문. "단독 사용 불가 = 스켈레톤"이라고 추론하면 안 됨.

### 스코프 (scope)
- `전역(global)`: 어느 기능(feature)에서든 사용 가능.
- `전용(local)`: 하나의 기능에서만 사용.
- 기준은 Figma 페이지가 아니라 기능(feature) 단위 (하나의 기능이 여러 페이지에 걸칠 수 있음).
- 이름에 스코프를 표시하지 않음 — 컴포넌트가 위치한 페이지가 스코프를 나타냄.

## 3. 네이밍 규칙

### 핵심 스키마 (레이어별 이름 형태)

| 레이어 | 이름 형태 | 예시 |
|---|---|---|
| 스켈레톤 | `.skeleton/{family}-{subgroup}` | `.skeleton/btn` |
| 템플릿 | `{family}-{subgroup}` | `btn-ghost` |
| 패턴 | `{family}-{subgroup}/pattern-{name}` | `btn-ghost/pattern-go-back` |

- `{subgroup}`은 선택 사항이며 항상 하이픈(`-`)으로 결합. 별도 슬래시 세그먼트로 만들지 않음.
- 슬래시(`/`)는 딱 두 가지 경우에만 사용:
  1. `.skeleton/` — 스켈레톤 레이어 표시
  2. `family-subgroup/pattern-name` — 패턴의 family와 이름 구분
  - 그 외의 모든 것(타입, 설명적 하위 이름 등)은 하이픈으로 붙임.
- 패밀리가 없는(어느 패밀리에도 속하지 않는) 컴포넌트: 해당 세그먼트를 생략.
  - 예: `.pattern-scrim` (패턴+빌딩블록, 패밀리 없음), `pattern-loading-overlay` (패턴, 퍼블리시됨, 패밀리 없음)
- 빌딩블록 + 패턴 조합: `.family-subgroup/pattern-name` 형태 유지 (예: `.btn-ghost/pattern-save-item`)

### 추가 규칙

1. **이름에 스코프를 넣지 않음.** 전역/로컬 여부는 페이지 위치로만 판단.
2. **이름은 "그것이 무엇인지"로 짓는다.** 위치나 구성 요소(ingredients)로 짓지 않음.
   - 나쁜 예: `btn-layout-with-cancel-and-confirm-buttons/pattern-x`
   - 좋은 예: `btn-layout/pattern-cancel-confirm`
3. **패밀리 = 공유된 정체성, 공유된 스켈레톤이 아님.** 같은 패밀리 안에서도 스켈레톤이 서로 다를 수 있음 (예: draggable 마커와 static 마커는 서로 다른 스켈레톤을 갖지만 "마커"라는 하나의 패밀리). 반대로 사람들이 서로 다른 이름으로 부르는 것(예: top-bar vs bottom-bar)은 형태가 비슷해도 별도 패밀리.
4. **"default", "main" 같은 이름을 패턴 이름으로 쓰지 않음.** 패턴은 자기 자신을 설명하는 구체적인 이름을 가져야 함 (`pattern-loading-overlay`는 그 자체로 완결된 이름).
5. **`pattern-`는 스켈레톤에 절대 붙지 않음.** 스켈레톤은 수정 가능한 속성이 0개여도 여전히 스켈레톤이지, 패턴이 아님.
6. **`pattern-`는 콘텐츠가 고정된 모든 패턴에 항상 붙음.** 대응하는 열린 템플릿이 실제로 존재하는지 여부와 무관 (독립적으로 만들어진 패턴도 동일하게 표시).

### 타입(type) 분화 규칙

같은 스켈레톤을 공유하고 모든 속성이 동일한 옵션들 → 하나의 컴포넌트 셋(variant)으로 관리.
어느 하나의 속성이라도 갈라지거나(예: 하나는 `floating` 속성이 있고 다른 하나는 없음), 합친 배리언트 수가 대략 50개를 넘으면 → 타입별로 별도 컴포넌트로 분리하고, 타입을 subgroup으로 이름에 포함 (`btn-ghost`, `btn-primary` 등 각각 별도 컴포넌트).

## 4. 페이지 배치 규칙

순서대로 판단하고 처음 해당되는 항목에서 멈춤:

```
1. 그 자체로 정체성을 가지는가?
   (사람이 아무 맥락 없이 이름만으로 요청할 만한가 — "버튼 추가해줘")     → 자기 전용 페이지

2. 하나의 기능(feature)에만 전용인가?                                    → 해당 기능 페이지

3. 정확히 하나의 패밀리만 이 컴포넌트를 구성 요소로 사용하는가?          → 그 패밀리의 페이지

4. 서로 무관한 2개 이상의 패밀리가 구성 요소로 사용하는가?               → 01 Foundations
```

- 규칙 3/4는 "누가 이 컴포넌트를 사용하는가"의 문제. "이 컴포넌트 안에 무엇이 중첩되어 있는가"와는 무관.
- 규칙 1은 다른 컴포넌트 안에서 자주 재사용되더라도 그 자체로 정체성이 있으면 (예: 버튼) 자기 페이지를 유지한다는 뜻.
- Foundations는 레이어와 무관하게 소유권 없는 모든 컴포넌트를 담을 수 있음 (스켈레톤뿐 아니라 완전히 고정된 패턴도 가능).
- Foundations는 비어 있어도 됨 — 미리 만들어둘 필요 없음.

### 페이지 번호 체계 (숫자 구간은 범용, 각 이름은 프로젝트별로 달라짐)

```
00       Cover & changelog
01       Foundations
02~49    각 패밀리 페이지 (프로젝트에 실제로 존재하는 패밀리 수만큼,
         Buttons/Inputs/Dialogs 등은 예시일 뿐 — 해당 프로젝트의
         실제 패밀리명으로 대체)
50~89    Feature — {기능명} (프로젝트의 실제 기능 단위로 대체)
90       Deprecated
```

이번 예시 프로젝트에서는 02~06이 아래와 같이 채워져 있었지만, 이는 이 프로젝트의 패밀리 목록일 뿐 다른 프로젝트에 그대로 적용되는 목록이 아닙니다:

```
02  Buttons
03  Inputs
04  Badges & chips
05  Dialogs & sheets
06  Top bar / GNB
```

새 프로젝트에서는 §4의 배치 규칙(1~4번)을 그 프로젝트의 실제 컴포넌트에 적용해서, 무엇이 "그 자체로 정체성을 가지는 패밀리"인지부터 판단하고 페이지를 구성해야 함.

- 패밀리 페이지: 해당 패밀리의 스켈레톤/템플릿/패턴 전부 포함. 빌딩블록은 페이지 상단에 `.` 접두사 섹션으로 모음.
- 기능(feature) 페이지: 해당 기능의 화면들 + `local-components` 섹션.

## 5. 라이프사이클 / 판단 트리거

### 언제 컴포넌트로 만들 것인가 (2회 규칙)

| 상황 | 조치 |
|---|---|
| 일회성 콘텐츠, 반복될지 불확실 | 컴포넌트로 만들지 않고 템플릿 인스턴스에 직접 입력 |
| 두 번째로 반복되거나, 처음부터 봐도 명백히 범용적 | 패턴으로 만들고, 처음부터 올바른 스코프로 배치 |
| 로컬 컴포넌트가 두 번째 기능에서도 필요해짐 | 전역으로 승격: 이름 변경, 페이지 이동 |
| 빌딩블록을 화면에 단독으로 배치할 필요가 두 번째로 생김 | `.` 제거하여 단독 사용 가능하도록 승격 |
| 템플릿 패밀리에 진짜 두 번째 타입이 생김 | 스켈레톤 추출 |
| 고정된 컴포넌트에 수정 가능한 형제가 필요해짐 | 그 아래에 템플릿을 추출하고, 기존 것은 그 위에 다시 고정 |

- **불확실한 경우에만** "두 번째 등장까지 기다리기"를 적용. 보자마자 명백히 범용적인 것(예: "확인" 버튼, "삭제 확인" 다이얼로그)은 처음부터 전역으로 만들어도 됨.
- **강등(전역→로컬)은 하지 않음.** 결과적으로 한 곳에서만 쓰였어도 전역 상태 유지.

### 스켈레톤을 언제 만들 것인가

다음 중 하나라도 해당 시 즉시 생성:
- 두 번째 비주얼 타입이 이미 존재하거나 로드맵에 있음
- 지오메트리가 다른 패밀리와 공유됨 (이 경우 Foundations로)
- 두 명 이상의 디자이너가 이 컴포넌트를 다룸

해당 없으면 생략하고 나중에 필요할 때 추출(템플릿 복제 → 색상/상태 제거 → 지오메트리만 남김 → 원래 템플릿의 내용을 새 스켈레톤 인스턴스로 교체).

## 6. 속성 소유권 / 토큰 규칙

| 속성 변경 시 영향 | 소유 레이어 |
|---|---|
| 형태, 크기, 간격, 배치 | 스켈레톤 |
| 보이는 방식(같은 면적) | 템플릿 |
| 의미/문구 | 패턴 |

- 스켈레톤: dimension 토큰만 바인딩(색상 절대 없음). 어떤 dimension 토큰을 쓸지는 `shape-token-rule.md` 참고.
- 템플릿: 모든 색상 토큰 바인딩. 라이트/다크모드는 이 레이어에서 처리. 정확히 어떤 색상 토큰(그룹/역할/상태)을 골라야 하는지는 `color-token-rule.md` 참고 — 이 문서는 "템플릿이 색상을 갖는다"까지만 정하고, 구체적인 토큰 선택 기준은 다루지 않는다.
- 패턴: 콘텐츠 바인딩(다국어 문자열 변수 포함). 텍스트 콘텐츠의 폰트 관련 속성은 `typography-token-rule.md`/`style-rule.md` 참고.
- `disabled` 등 상태 속성은 완전히 고정된 패턴을 거치더라도 항상 화면까지 전달되어야 함(상태를 노출하지 않는 패턴은 버그).
- 멀티 브랜드: 스켈레톤 공유, 템플릿은 브랜드별(색상=브랜드), 패턴은 제품별. 브랜드마다 지오메트리가 다르면 별도 스켈레톤(템플릿 오버라이드 아님).

## 7. 자주 발생하는 오류 패턴

| 오류 | 올바른 처리 |
|---|---|
| 단독 사용 불가 → 스켈레톤이라고 잘못 추론 | 빌딩블록 플래그와 레이어는 별개 질문 (섹션 2 참고) |
| 수정 가능한 속성이 없다고 스켈레톤에 `pattern-` 부여 | 스켈레톤은 절대 `pattern-`를 붙이지 않음 |
| 패턴의 family/type 세그먼트를 슬래시로 분리 | 슬래시는 `.skeleton/`과 `family/pattern-name` 구분에만 사용, 타입은 하이픈 |
| 컴포넌트 이름에 위치(feature, 페이지)나 구성 요소를 포함 | 이름은 "그것이 무엇인지"만 반영 |
| 사용처가 여러 곳이라는 이유로 Foundations로 이동 (정체성 있는 컴포넌트인데도) | 정체성이 있으면(예: 버튼) 재사용 빈도와 무관하게 자기 페이지 유지 |
